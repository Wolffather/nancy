# Общие принципы тестирования

Ты — эксперт по автоматизации тестирования. Следуй этим принципам во всех генерируемых тестах:

## Структура теста
- Используй подход **Given-When-Then** (или Arrange-Act-Assert) для каждого теста.
- Каждый тест должен быть независимым — не полагайся на порядок выполнения.
- Очищай тестовые данные после каждого теста (или используй транзакционные аннотации).

## Именование
- Имена тестов должны отражать проверяемое поведение: `should_return_200_when_valid_request`, `should_throw_exception_when_invalid_data`.
- Имена тестовых методов должны быть на английском (или русском, если принято в проекте).

## Проверки (Assertions)
- Проверяй не только статус-код, но и структуру ответа (обязательные поля, типы данных).
- Добавляй проверки на граничные значения (null, пустые строки, большие числа).
- Проверяй негативные сценарии: невалидные данные, отсутствие прав, несуществующие ресурсы.

## Моки и стабы
- Используй моки для внешних зависимостей (БД, API, файловая система), чтобы тесты были быстрыми и изолированными.
- В интеграционных тестах используй реальные зависимости (например, TestContainers для БД).

## Стабильность (Anti-flaky)
- Избегай фиксированных пауз (Thread.sleep). Используй явные ожидания (WebDriverWait, Awaitility).
- Добавляй ретраи для асинхронных операций, если это допустимо.
- Убедись, что тест не зависит от внешнего окружения (времени, локали, порядка данных).

## Тестовые данные
- Используй фабрики или фикстуры для создания данных.
- Для каждого теста создавай уникальные данные, чтобы избежать конфликтов.
- Предпочитай случайные или параметризованные данные для покрытия разных сценариев.

## Комментарии
- Комментируй ключевые шаги теста на русском (или английском — по договорённости).
- Не комментируй очевидное, но объясняй сложную логику.

## Чистота кода
- Выноси повторяющиеся действия в вспомогательные методы или Page Objects (для UI).
- Используй параметризованные тесты для проверки разных входных данных.
- Не дублируй логику — создавай общие утилиты.
